## Sprint 1: Project Foundation

**Goal:** A running skeleton — empty but real, end to end. Prove the wiring works before any feature logic exists.

**Architecture for this sprint:**
Three containers via Docker Compose: `postgres` (empty DB, just proving connectivity), `backend` (FastAPI with a `/health` endpoint that also checks DB connectivity), `frontend` (React app with one page that calls `/health` and displays status). No business logic yet — this sprint is purely about the scaffolding and the seams between services.

**Implementation tasks:**
1. Repo structure: `backend/`, `frontend/`, `infra/` (or `docker-compose.yml` at root — your call, I'll ask).
2. `backend`: FastAPI app, `pydantic-settings` config, SQLAlchemy engine pointed at Postgres, `GET /health` returning `{status, db_connected}`.
3. `frontend`: Minimal Vite + React app, one page fetching `/health` and rendering the result — proves CORS/networking is correct.
4. `docker-compose.yml`: three services, a named volume for Postgres data, `.env.example` for config, sensible service dependencies (`depends_on` + a DB healthcheck).
5. `README` section: how to run it (`docker compose up`), what you should see.

**Testing:**
- `docker compose up` brings up all three services cleanly.
- Backend `/health` returns 200 with `db_connected: true`.
- Frontend loads and displays the health status fetched from the backend.
- One basic backend test (e.g. via `pytest` + `httpx` TestClient) hitting `/health`.

**Learning objectives:**
- Why a reverse-proxy-free dev setup works differently from production (CORS, ports, service DNS names inside Compose).
- Why we check DB connectivity in `/health` rather than just returning a static 200 — health checks should verify real dependencies.
- Docker Compose networking basics: service name resolution, `depends_on` vs. actual readiness.

**Possible future improvements (not now):** structured logging, request tracing, a proper `/health` vs `/ready` split (relevant again in Sprint 7 for K8s probes).

**Decisions locked in:**
- Repo layout: flat (`backend/`, `frontend/`, `docker-compose.yml` at project root).
- Python tooling: `uv`.
- LLM provider (used from Sprint 3 onward): locally hosted **Qwen via Ollama** — no API keys, fully offline. Note for Sprint 3/Compose: since Ollama already runs on the host, the backend container will need to reach it via `host.docker.internal` (or a Compose Ollama service, decided when we get there) rather than `localhost`.

## Sprint 2: Fitness Data Management

**Goal:** Real personal fitness data, persisted and queryable — the substrate every later AI feature reads from and writes to. No AI yet.

**Architecture for this sprint:**
- One generic `workouts` table (shared fields: date, duration, notes, calories...) + sport-specific detail tables (`football_sessions`, `hyrox_sessions`, `running_sessions`), each 1:1 with a workout via `workout_id`. Rejected the alternative of one wide table with 40 nullable columns — harder to query/validate and doesn't extend cleanly for future sports.
- `users` table holds profile/goals/preferences even though there's still only a single default user (no auth yet) — the shape is correct for when multi-user auth gets added later, rather than needing a schema rewrite.
- `injuries` table, optionally linked to a `related_workout_id`.
- **Alembic** for migrations, not `create_all()` — schema changes are tracked and versioned from day one, since real projects almost never get the schema right on the first try.
- `POST /workouts` accepts the generic fields plus an optional nested `football`/`hyrox`/`running` detail object depending on `exercise_type` — one call logs both the workout and its sport-specific detail.

**Implementation tasks:**
1. SQLAlchemy 2.0 models (`Mapped[...]` style) for all 6 tables, in `app/models/`.
2. Alembic set up, wired to read `DATABASE_URL` from the same `Settings` object the app uses (not a separate hardcoded URL) and to `Base.metadata` for autogenerate support.
3. Initial migration, autogenerated and reviewed, creating all 6 tables.
4. Pydantic schemas (`Create`/`Update`/`Read` variants) in `app/schemas/`.
5. `get_db` FastAPI dependency (session-per-request, always closed).
6. CRUD routes: `users`, `workouts` (with nested sport-session creation and `exercise_type`/date-range filtering on list), `injuries`.
7. Backend container now runs `alembic upgrade head` before starting Uvicorn.

**Testing:**
- 12 pytest tests, run against a **real Postgres** (not SQLite/mocks) — necessary because the schema uses Postgres-native `ARRAY` and `ENUM` types that SQLite can't represent honestly. Each test runs inside a transaction that's rolled back afterward, so tests never leave data behind.
- Manual end-to-end verification through the actual `docker compose` stack: create a user, log a football workout with a nested session, log an injury, list/filter workouts — all through real HTTP calls to the containerized API.

**Learning objectives:**
- Why sport-specific detail tables beat one wide table, and when the opposite would be true (few sports, mostly-shared fields).
- Migrations vs. `create_all()`: what a migration actually buys you (safe schema evolution, rollback, review-before-apply) that auto-creation can't.
- SQLAlchemy 2.0's typed `Mapped[...]` declarative style.
- A real Python footgun hit and fixed along the way: naming a field the same as its type (`date: date | None = None`) breaks, because Python evaluates and stores the default value *before* evaluating the annotation — by the time the annotation runs, the name has already been shadowed. Fixed by aliasing the import (`from datetime import date as date_`).
- Session-per-request pattern (`get_db` as a FastAPI dependency) vs. a single global session.

**Possible future improvements (not now):** pagination on list endpoints, soft-deletes instead of hard deletes, auth once multi-user support is needed, a `PATCH` on sport-session sub-objects (currently only the parent workout's generic fields are patchable).

## Sprint 3: Basic LLM Integration

**Goal:** A working chat interface talking to a real local LLM (Ollama + Qwen). No agent, no tools, no data access yet — just understand what a raw LLM chat request/response actually looks like before Sprint 5 wraps it in orchestration.

**Architecture for this sprint:**
- Called Ollama's `/api/chat` REST endpoint directly via `httpx`, deliberately **not** through LangChain yet — introducing that abstraction now would hide the exact mechanics this sprint exists to teach. LangChain/LangGraph arrives in Sprint 5 when tool-calling and multi-step orchestration actually need it.
- **Conversation state lives entirely on the client.** The React app holds the message array in local state and sends the *full* history on every turn; the backend is stateless per-request — it just prepends a system prompt and forwards to Ollama. Persisting conversations to Postgres is a natural Sprint 6 addition once personalization needs to reference past chats, not before.
- A small `SYSTEM_PROMPT` ([app/llm/prompts.py](../code/projects/fitness_coach_ai/backend/app/llm/prompts.py)) gives the model a fitness-coach persona and is explicit about what it *doesn't* have access to yet (workout history, injuries, a knowledge base) — first hands-on prompt engineering.

**Implementation tasks:**
1. `Settings.ollama_base_url` / `ollama_model` — same `pydantic-settings` pattern as `database_url`.
2. [app/llm/ollama_client.py](../code/projects/fitness_coach_ai/backend/app/llm/ollama_client.py) — thin async wrapper over Ollama's chat API, raising a typed `LLMServiceError` on failure.
3. `ChatMessage`/`ChatRequest`/`ChatResponse` Pydantic schemas, `POST /chat` route.
4. React `Chat` component: message list + input, full-history-per-turn.
5. `docker-compose.yml`: backend gets `OLLAMA_BASE_URL=http://host.docker.internal:11434` (Ollama runs on the host, not in a container) plus `extra_hosts: host.docker.internal:host-gateway` so that resolves on Linux Docker too, not just Mac/Windows.

**Testing:**
- Unit tests mock the LLM call (`pytest-mock`) to verify route/schema behavior (happy path, `503` when Ollama's unreachable, `422` on a malformed body) without needing a model loaded — fast, deterministic.
- Manual end-to-end verification against the **real** local Ollama (`qwen2.5:3b`), both running the backend directly on the host and through the full `docker compose` stack — confirmed the football/injury example questions from the app concept get real, on-topic answers, and confirmed the container can actually reach host Ollama via `host.docker.internal`.

**Learning objectives:**
- What a raw LLM chat completion request/response actually contains (`{"model", "messages": [{"role", "content"}], "stream"}` in, `{"message": {"role", "content"}}` out) — this is the shape LangChain will abstract away starting Sprint 5, so it's worth having seen it bare first.
- System prompts as the mechanism for persona + honesty about capability boundaries ("ask rather than guess" when data is missing) — this becomes load-bearing once Sprint 5 adds real tools the model can choose to call.
- Client-held vs. server-held conversation state, and why "server is stateless per request" is the simpler starting point.
- Container networking for a host-run dependency: `host.docker.internal` lets a container reach services running on the host machine (as opposed to `depends_on` + a service name, which is for container-to-container).

**Possible future improvements (not now):** streaming responses (Ollama supports `stream: true`; UI would need to handle incremental tokens), persisting conversations to Postgres, swapping the direct `httpx` client for LangChain's Ollama wrapper once Sprint 5 needs the rest of LangChain anyway.

## Sprint 4: RAG System

**Goal:** Expert fitness knowledge, retrievable by meaning (not keyword), and folded into chat responses. Naive RAG — always retrieve, no judgment about whether a question needs it — since that judgment call is Sprint 5's job.

**Architecture for this sprint:**
- **Knowledge base**: original, concise markdown docs I authored per domain ([app/rag/knowledge/](../code/projects/fitness_coach_ai/backend/app/rag/knowledge/)) — `football.md`, `hyrox.md`, `bodybuilding.md`, `injury_prevention.md` — covering the sub-topics from the app concept (position-specific conditioning, sled programming, hypertrophy principles, ankle-sprain recovery, etc.).
- **Chunking**: split on `##` headings — each chunk is one topically coherent section, avoids the mid-thought splits fixed-length chunking can cause.
- **Embeddings**: `nomic-embed-text` via Ollama (already pulled), 768-dim vectors.
- **Storage**: `pgvector` in the same Postgres instance — a `knowledge_chunks` table with an HNSW index (`vector_cosine_ops`) for fast approximate similarity search. The extension itself (`CREATE EXTENSION vector`) and the HNSW index aren't things Alembic's autogenerate can detect from SQLAlchemy models alone — both were added by hand to the generated migration.
- **Retrieval**: cosine distance search, done in Postgres via pgvector's `<=>` operator (through SQLAlchemy's `.cosine_distance()`), not pulled into Python and ranked there — the whole point of the index.
- **Naive RAG wired into `/chat`**: the latest user message is always embedded and searched; top-3 chunks get folded into an extra system message before the LLM call. No decision-making about *whether* retrieval was needed — that's explicitly deferred to Sprint 5's agent, which will decide per-question whether DB lookup, RAG search, both, or neither apply.
- **Ingestion is a manual script** (`uv run python -m app.rag.ingest`), not an HTTP endpoint or something that runs automatically on container start — content population is a different concern from schema migration, and re-running it is idempotent (each file's existing chunks are cleared and reinserted).

**Implementation tasks:**
1. `KnowledgeChunk` model with a `pgvector` `Vector(768)` column; migration hand-edited to add the extension and HNSW index around the autogenerated table DDL.
2. `embed_text()` added to the Ollama client alongside Sprint 3's `send_chat()`.
3. `app/rag/chunking.py` (pure, no I/O — easy to unit test), `app/rag/ingest.py` (file → chunks → embeddings → DB), `app/rag/retriever.py` (query → embedding → pgvector similarity search).
4. `POST /rag/search` — a dedicated endpoint for manually inspecting retrieval quality, independent of `/chat`.
5. `/chat` updated to call the retriever for the latest user message and inject results as an extra system message ([app/llm/prompts.py](../code/projects/fitness_coach_ai/backend/app/llm/prompts.py)'s `build_knowledge_context()`).

**Testing:**
- Chunking: pure unit tests, no DB/embedding needed.
- Ingestion: real DB (rolled back per test), embedding mocked — verifies chunking + storage + idempotent re-ingestion, independent of embedding quality.
- Retrieval ordering: seeded hand-crafted unit vectors (aligned/orthogonal/opposite) so cosine distance is exactly predictable (0 / 1 / 2) — proves the pgvector query logic is correct without depending on real embedding semantics.
- **Hit a real test-isolation gap here**: the retriever tests initially failed because the *real* ingested knowledge base (already committed to the dev DB from running the ingestion script) was visible inside the test transaction alongside the seeded test vectors, polluting similarity ordering. Fixed by clearing `knowledge_chunks` at the start of the fixture — safe, because it happens inside the same rolled-back test transaction, never touching the real committed data (verified by checking row counts before/after).
- Manual retrieval-quality check via `/rag/search` with real embeddings — e.g. "My ankle was recently injured, how do I recover safely?" correctly surfaced "Ankle Sprain Recovery Principles" at distance 0.23, ahead of everything else.
- Full end-to-end through `/chat`, both on host and through `docker compose` — e.g. asking the sled-push and muscle-gain-while-playing-football questions from the app concept produced answers that concretely reflected the ingested knowledge (specific set/rest schemes, lower-body/posterior-chain emphasis) rather than generic LLM output.

**Learning objectives:**
- Chunking strategy trade-offs: heading-based (semantic, this project) vs. fixed-length with overlap (simpler, more common at scale, can split mid-thought).
- Why similarity search happens *in the database* via an index (HNSW) rather than fetching all rows and computing distances in Python — this is the actual point of a vector database/extension.
- Migrations sometimes need hand-written DDL — extensions and specialized index types aren't things an ORM's metadata can express, so autogenerate can't produce them; you write that part yourself and review it like any other migration.
- **Naive vs. agentic RAG**: always-retrieve (this sprint) is simple and works, but wastes a retrieval+embedding call on questions that don't need expert knowledge (e.g. "hi") and can inject irrelevant context on off-topic questions. An agent that decides *whether* to search (Sprint 5) is strictly more capable, at the cost of another LLM call to make that decision.
- A concrete instance of test data isolation being harder than it looks when a table is meant to hold long-lived reference/seed data alongside per-test data.

**Possible future improvements (not now):** domain-aware routing (route a Hyrox question to the Hyrox namespace first, per [ARCHITECTURE.md](../code/projects/fitness_coach_ai/ARCHITECTURE.md)'s original RAG design, rather than searching the whole corpus), chunk overlap for longer docs, citing sources in the chat response, a larger/real knowledge corpus instead of the small authored set.
